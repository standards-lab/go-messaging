## Task brief · service-events

```
Problem       go-web-service emits no events. go-messaging v0.1.0 has the outbox,
              the relay, and the NATS provider, but no service uses them, so the
              composite Postgres-and-blob case the spike left open is unproven: an
              event committed in the same transaction as a blobfs upload's complete
              step. blobfs's write completes on the pool with no hook, so the
              service stages its own write protocol to get that transaction. The
              relay writes the messaging set's tables but cannot hold the quiesce
              gate, so a schema reset can run while a relay pass is in flight. And
              the nats provider publishes to <prefix>.<type>, which stutters once a
              type carries its service. This task moves the service to go-core
              v0.10.0; adds a gate option to go-messaging's Runtime and makes the
              nats subject the event type itself, releasing go-messaging v0.2.0 and
              nats/v0.2.0; runs the messaging runtime on NATS in the service as its
              stream's owner; emits web-service.document.file.uploaded from the
              upload's complete step; proves it in the integration tier; and adds a
              slab command that prints the stream live.
Behaviors     1. go-web-service and its slab module require go-core v0.10.0, and the
                 service's currency command exits 0. Once the later slices add them,
                 go-messaging v0.2.0, postgres/v0.1.0, and nats/v0.2.0 are required,
                 and the NATS image is nats:2.15.1-alpine.
              2. go-messaging's Runtime takes an option that holds a gate, a value
                 with Shared(ctx) (release func(), err error), which go-core's
                 reactor.Gate satisfies. The relay takes the gate shared before it
                 opens each row's transaction, on a context the drain can cancel,
                 and releases it once the row commits or rolls back, the drain's
                 last pass included on its own bounded context. A relay waiting on a
                 held gate opens no transaction; a wait the drain ends claims no row
                 and reports nothing.
              3. Under the same option, each delivery a Consume reactor handles
                 holds the gate shared for the handler's whole call. A wait the
                 drain ends hands nothing to the handler and leaves the event for
                 redelivery. The option's doc says a delivery that waits past
                 AckWait is redelivered and counts against MaxDeliver. Without the
                 option, the relay and Consume behave exactly as in v0.1.0.
              4. go-messaging's nats provider publishes each event to its type as
                 the subject. The configured prefix is the namespace every published
                 type must start with: the owner's stream captures <prefix>.>, a
                 non-owner's Start checks the stream captures it, and Publish
                 refuses a type outside it as permanent, naming the type and the
                 prefix. Subscriptions filter on the type as the subject.
              5. The base CHANGELOG has a v0.2.0 section naming the gate option; the
                 nats CHANGELOG has a nats/v0.2.0 section marking the subject change
                 Breaking. The postgres module is unchanged and untagged.
              6. The service has a messaging block (APP_MESSAGING_*) and a nats block
                 (APP_NATS_*). The base configuration sets source web-service,
                 stream WEB_SERVICE, prefix web-service, and the service as the
                 stream's owner. An invalid block fails startup and names the block.
              7. At startup the messaging migration set runs, then blobfs's, then the
                 service's own. The messaging statements are verified with every
                 other store's; a schema without the messaging set fails startup.
                 The database admin's migration listings and state reset cover the
                 messaging set.
              8. /readyz lists a broker check and a relay check. With NATS down, the
                 service is not ready and keeps running; once NATS is back, it is
                 ready again with no restart.
              9. A document file upload that completes commits exactly one
                 web-service.document.file.uploaded event, in the transaction that
                 makes the file available, published on the subject
                 web-service.document.file.uploaded. Its CloudEvents subject is the
                 file id. Its data is the file id, organization, directory, name,
                 content type, size, ETag, and version, never the content.
              10. An upload whose put or completion fails commits no event, and its
                  row is abandoned exactly as blobfs's own write abandons it. A
                  completion refused because a sweep reached the row first deletes
                  the stored object and commits no event. Every other result the API
                  returns for an upload is unchanged.
              11. Logo writes, seeds (at startup and on a state reset), the admin
                  layer, and every other command emit nothing.
              12. The relay publishes each committed event to the service's stream.
                  A stop between the commit and the publish loses no event: the next
                  start publishes it.
              13. While a schema-changing admin verb holds the gate, the relay claims
                  no row; the verb waits for a row already claimed to settle. A
                  state reset with events pending returns, and afterwards the relay
                  is ready with no database error reported.
              14. The service drains in order: the server, then the document
                  service's producers, then the relay with its last pass, then the
                  broker and the database. An event committed during the drain is
                  published before the process exits.
              15. The integration tier runs NATS beside PostgreSQL and Azurite, on an
                  offset port, in its own compose project, and subscribes to the
                  service's stream through go-messaging's nats broker as a non-owner.
                  After an upload, exactly one uploaded event arrives, with the
                  file's metadata; after a failed upload, none.
              16. A slab command subscribes to the stream through nats.go's ordered
                  consumer over the nats broker's connection, decodes each message
                  with go-core's event.Decode, and prints each event's type, id,
                  subject, time, and data until interrupted. By default it prints
                  events published after it starts; --from-start replays the stream
                  first. On exit it leaves no consumer on the server and returns 0.
                  When no NATS server answers, it exits nonzero and names the mise
                  task that brings the stack up.
              17. The service's README and doc comments describe the messaging
                  layer: the runtime, the broker and relay as nodes, stream
                  ownership, the subject as the type, the event's type and data as
                  public API, the convention that a public command emits one event
                  in the transaction that makes it true, the staged write protocol
                  bound for blobfs, and the gate shared with the relay. [Unreleased]
                  records the additions and the pin moves.
Test seams    The service as the integration tier runs it: its HTTP API, its
              /readyz, and its stream as a non-owner subscriber sees it. Unit seams:
              go-messaging's Runtime (relay and Consume over the memory provider and
              pgtest, with a test gate), the nats Broker over natstest, and the
              service's staged write protocol over the data package's surface.
Slices        Phase A, go-messaging, released before the service builds on it:
              1. go-messaging gate option (behaviors 2-3, 5 base). Demo: a Runtime
                 test and the postgres integration suite show the relay waiting on
                 an Exclusive holder and resuming after.
              2. go-messaging nats subject = type (behaviors 4, 5 nats). Demo: the
                 nats integration suite publishes <prefix>.x.y to subject
                 <prefix>.x.y and refuses a type outside the prefix.
                 Phase A ends with go-messaging's standards and spec reviews and a
                 go-messaging release brief; on acceptance its pull request merges
                 and v0.2.0 and nats/v0.2.0 are tagged (Releasing), before slice 3.
              Phase B, go-web-service, on the released tags:
              3. Upgrade go-web-service: go-core v0.10.0 in both modules
                 (behavior 1, first sentence), with an [Unreleased] entry. Demo: the
                 currency command exits 0 and the check passes.
              4. Messaging runtime in the service, no events yet (behaviors 1,
                 6-8, 13-14): pins on the released go-messaging v0.2.0,
                 postgres/v0.1.0, and nats/v0.2.0, config blocks, migration set and verify, broker
                 and runtime nodes, relay after the schema with the document node
                 using it, the gate passed in, NATS in compose and the integration
                 task. Demo: `mise run integration` passes with the new probe
                 checks; a state reset under a running relay returns cleanly.
              5. Upload emits from its complete step (behaviors 9-12, 15): the
                 staged write protocol, the event kind in the document layer, the
                 upload run through it. Demo: integration cases for an upload
                 (exactly one event) and a failed upload (none).
              6. slab event watch (behavior 16). Demo: with the stack up, it prints
                 the event of a file uploaded through slab's storage scenario, and
                 Ctrl-C leaves no consumer.
              7. Docs (behavior 17). Demo: the README's messaging section reads as
                 the guide to adding a second event.
Out of scope  Events for any command other than the document upload (task
              event-coverage); promoting the write protocol to blobfs (task

Door          One-way for the go-messaging v0.2.0 and nats/v0.2.0 tags, which reach
```
