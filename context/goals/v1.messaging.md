Problem       Only the document upload emits an event. The 12 other public commands
              that change state commit nothing to the outbox, so their changes are
              invisible outside the service. Organization Create, Edit, and Delete each
              run as one statement on the pool, so there is no transaction for an event
              to join. blobfs's file delete runs its first transaction with no hook.
              Seeds and the admin layer emit nothing by ruling, so a consumer can't
              tell that the state was reset and reseeded. The admin service's reset
              also has no point between the schema apply and the seed where the
              service could write a reset event. The four-token naming rule doesn't
              fit commands on a domain itself: it would give
              web-service.organization.organization.created. This task does four
              things:
              - adds a reset hook to go-database's admin service and releases
                go-database v0.9.0;
              - emits one event from each of the 12 commands, from every seed write,
                and from the state reset, under the two-form naming rule;
              - stages blobfs's file delete in the service with a hook, bound for
                blobfs;
              - proves all of it in the integration tier.
Behaviors     1. go-database's base module requires go-core v0.10.0, and its workflows
                 pin jdx/mise-action v5.1.2. Its currency command exits 0.
                 [Unreleased] records the new requirement and marks it Breaking,
                 because it pulls go-core v0.8.0's narrower readiness checks into an
                 importer's build. v0.8.0's entry marked its own pin raise the same
                 way.
              2. go-database's admin Options take a reset hook, a function of the
                 context and the resolved state name.
                 - Reset calls the hook once, after every set is applied and before
                   the state's seed set.
                 - Start, Seed, Status, Up, Down, Steps, and Force never call it.
                 - With no hook, Reset behaves exactly as in v0.8.0.
                 - If the hook returns an error, Reset stops before seeding and
                   reports the failure with the step named. The schema is left
                   applied and unseeded, as a failed step leaves it now.
                 - The doc says Reset's revert drops everything the consumer's sets
                   hold, an outbox's unpublished rows included.
              3. The base CHANGELOG has a v0.9.0 section naming the hook and the
                 go-core requirement. The postgres module is unchanged and untagged.
              4. go-web-service requires go-database v0.9.0, and its currency command
                 exits 0.
              5. Each of these commands commits exactly one event, in the transaction
                 that makes its change true. Event types:
                   organization Create/Edit/Transfer/Delete
                     web-service.organization.created / .edited / .transferred / .deleted
                   PutLogo / DeleteLogo
                     web-service.organization.logo.uploaded / .deleted
                   CreateDirectory / MoveDirectory
                     web-service.document.directory.created / .moved
                   DeleteDirectory and DeleteBranch
                     web-service.document.directory.deleted
                   DeleteFile / MoveFile
                     web-service.document.file.deleted / .moved
                 web-service.document.file.uploaded is unchanged. Each event is
                 published on its type as the subject. Its CloudEvents subject is the
                 id of the entity the type names: the organization, the logo's file,
                 the directory, or the file.
                 A command that fails commits no event. This includes failures from a
                 version guard, a scope check, a cycle, or a conflict. Every result the
                 API returns is unchanged.
              6. Organization Create, Edit, and Delete each run in one transaction that
                 holds the change and its event. Transfer emits inside its existing
                 tree-locked transaction.
              7. An event's data is the entity's stored state after the command, under
                 the API's field names, with organization_id and version. It carries
                 no derived path, no timestamps, and no earlier state (a move or a
                 transfer carries only the new parent).
                 - Organization: organization_id, parent_id, code, name, version.
                 - Directory: directory_id, organization_id, parent_id, name, version.
                 - A moved file: the same fields as an uploaded file.
                 - Logo upload: file_id, organization_id, content_type, size, etag,
                   version.
                 - A deleted entity: its id, organization_id, and the version the
                   delete left it at, or for a row the delete removed, the version it
                   was removed at.
              8. PutLogo commits logo.uploaded in the transaction that activates the
                 logo and releases the logo it replaces. It commits no logo.deleted for
                 the replaced logo. An activation that rolls back commits no event.
                 DeleteLogo commits logo.deleted in the transaction that releases the
                 logo. A purge that fails after either commit doesn't affect the event.
              9. DeleteBranch commits one directory.deleted for the marked directory,
                 in the mark's transaction, and no event for anything beneath it. A
                 mark that finds the directory already deleting (blobfs's mark counts
                 no directory) commits no event and still answers as it does now.
              10. DeleteFile runs through a delete protocol staged in the service's sdk
                  package beside the staged write. It reproduces blobfs's two-phase
                  delete from blobfs's exported Files.Hold, Files.Delete, and
                  PurgeFile, and adds a hook in the delete's first transaction, where
                  file.deleted commits.
                  - A delete of a file that is already deleting is the retry
                    (Files.Hold reports a DeletingError). It commits no event and still
                    finishes the purge.
                  - Every result the API returns for a file delete is unchanged.
                  - The protocol is bound for blobfs and takes no messaging
                    dependency.
              11. When an organization's first write under the root alias creates its
                  document root, the transaction that creates the root commits
                  directory.created for it, whether a request or a seed made the
                  write. The data shows the root as the API presents it: parent_id null

                  concurrent first write, commits no root event. The write's own event
                  follows in its own transaction.

                  in the transaction that creates the entity:

                  that rolls back commits none.

                  its CloudEvents subject are the state's name. It commits through the
                  reset hook, after the schema is applied and before the seed, so it
                  comes before the reset's seed events on the stream. The reset commits
                  no per-entity delete events. Up, Down, Steps, and Force commit no
                  event. The standalone seed verb commits only the per-entity seed
                  events.
              14. Reads, the sweep's reclamation, and the purge that finishes a delete
                  commit no event.
              15. In the unit tier, each event kind's every data field and subject are
                  checked, and so is a failing command committing nothing (the
                  transaction rolls back).
              16. The integration tier runs on the running stack with a non-owner

                  - the seeds case now finds the startup seed's events;
                  - a reset delivers web-service.database.reset before its seed events;
                  - a seed rerun over a seeded schema delivers nothing.
              17. The README's messaging section and the doc comments state:
                  - the naming rule;
                  - the one-event convention;
                  - that seeds emit and the reset emits one event, while schema verbs
                    and retries emit nothing;
                  - that a reset loses unpublished events, because its revert drops
                    the outbox;
                  - the staged delete and ensure protocols, bound for blobfs;
                  - each event's type and data as public API.
                  [Unreleased] records the events and the go-database pin.
Test seams    The service as the integration tier runs it: its HTTP API, its admin
              API, and its stream as a non-owner subscriber sees it. Unit seams:
